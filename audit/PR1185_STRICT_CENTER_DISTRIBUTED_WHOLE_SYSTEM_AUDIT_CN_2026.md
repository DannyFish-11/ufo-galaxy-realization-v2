>
> 审计方法：只用真实代码做证据。代码能证明就写“已证明”；代码不能证明就写“未证明”。
>

## 0. 先说 PR #1185 还没审完的点

PR #1185 的剩余盲点（本次必须补齐）：

1. 把系统过度简化成“V2 中心执行 + Android 子执行”，没有把“本地链路 + 跨设备链路并存”当成同等主链。
2. 没把“中心协调器存在”与“完整中心智能体存在”明确分开。
3. 对 mesh / NATS / WebSocket 的关系说得不够硬，没把它们在真实代码中的职责边界讲清楚。
4. 对 panel/dashboard/桌面壳的缺口审计不够，容易让人误以为“后端有了就算系统完成”。
5. 对 TypeScript/全栈、多模态交互、端到端可用体验的剩余建设清单不够结构化。

---

## 1) 意图中的完整系统模型（白话）

这套系统的目标不是“一个中心 + 一个从设备”。

目标是：手机、平板、电脑都能加入同一系统；每个设备既能自己做事，也能参与帮别的设备做事；
本地链路和跨设备链路都要成立；系统要有中心智能层做统一规划和治理，也要有分布式执行能力；
最终用户看到的是“一个能用、能看、能追踪、能恢复”的完整体验。

这意味着：

- 设备可自运行；
- 设备可协同运行；
- 本地执行与跨设备执行共存；
- mesh / NATS / WebSocket 是连接机制，不是同一层概念；
- 面板和可用体验是系统核心，不是附属页面。

## 2) 当前双仓真实代码系统是什么

### 2.1 V2 侧可证明事实

- 中心编排骨架存在：`core/openclawd.py`、`core/command_router.py`。
- 设备路由存在：`galaxy_gateway/device_router.py`。
- WebSocket 设备入口存在：`galaxy_gateway/routes/websocket.py`。
- 结果收敛与投影存在：`core/unified_result_ingress.py`、`core/routes/projection.py`。
- Mesh 协调器存在：`core/mesh_coordinator.py`。
- NATS 总线存在，但可 no-op：`core/nats_bus.py`（`GALAXY_NATS_URL` 未配置时可降级）。
- 当前桌面主可见面是状态看板，不是完整交互助手：`windows_client/status_board_v2/app.py`。
- Web 控制台是原生静态页：`static/operator-console/index.html`。

### 2.2 Android 侧可证明事实（按仓内锚点引用）

- 持久连接与消息主链：`app/src/main/java/com/ufo/galaxy/network/GalaxyWebSocketClient.kt`。
- 连接服务与任务接收：`app/src/main/java/com/ufo/galaxy/service/GalaxyConnectionService.kt`。
- 本地执行流水线：`app/src/main/java/com/ufo/galaxy/agent/AutonomousExecutionPipeline.kt`。
- 说明：Android 不是“纯被动终端”，它有本地执行能力；但跨设备协同完整闭环是否成熟，需要联合证据继续证明。

## 3) 已匹配与未匹配（显式三态）

### 3.1 已真实闭合（REAL_CLOSURE）

- V2 ↔ Android 的 WebSocket 主消息通道已形成稳定主干。
- 设备注册、任务下发、结果回传、投影展示这些基础路径已有代码落点。

### 3.2 部分闭合（PARTIAL_CLOSURE）

- 多设备协作：有路由与 mesh 组件，但“多设备联合执行 + 恢复 + 一致验收”仍缺统一强证据。
- 中心智能体：有编排骨架，但计划、记忆、多设备编队、失败恢复、可解释输出还未形成完整产品闭环。
- 操作面：有 status board 与 operator-console，但不足以支撑“一线可操作 + 一键追因 + 一键恢复”。

### 3.3 伪闭合风险（FAKE_CLOSURE）

- “有端点/有字段/有面板”不等于“完整可用体验已完成”。
- “有 mesh/NATS 代码”不等于“多设备协同在真实网络里已稳定可用”。
- “有中心协调代码”不等于“中心智能体机制已经完整”。

## 4) 中心智能体完整性审计（重点）

结论：**当前可确认“中心协调层存在”，但“完整中心智能体”尚未成立。**

区分：

- 已有：请求接入、路由分发、结果汇聚、状态投影。
- 缺失/不完整：
  1. 跨设备统一规划器（明确的多设备计划图与执行策略）
  2. 持续记忆闭环（跨会话记忆写入、检索、冲突解决）
  3. 统一工具编排（跨设备工具能力选择与回退策略）
  4. 故障恢复编排（自动重试、替代设备、恢复路径可见）
  5. 可持久状态机（任务级状态可追溯、可重放、可审计）
  6. 面向操作者的推理可见性（“系统为何这样决策”）

这部分直接回答：
“coordinator/dispatcher 已有” ≠ “true central agent 已完成”。

## 5) 多设备协作审计

必须分四类看：

1. 自设备执行：设备自己完成自己的任务（已见代码路径）。
2. 委托执行：中心把任务发给某一设备（已见代码路径）。
3. 中继执行：设备 A 经中心转交给设备 B（有结构能力，闭环证据不足）。
4. 多设备协同执行：多个设备分工同一目标（组件存在，统一验收闭环未成熟）。

当前差距：

- capability discovery、role assignment、协作冲突解决仍偏弱；
- “手机+平板+电脑联合完成一个目标”的产品级稳定性未被充分证明。

---

## 6) mesh / NATS / WebSocket 在当前系统各自做什么

- **WebSocket**：当前 V2 ↔ Android 主通道（实时命令/结果主干）。
- **mesh**：覆盖在主通道之上的协作/加速机制，受网络条件和接线完整度影响。
- **NATS**：分布式消息总线能力；在未配置 `GALAXY_NATS_URL` 或无依赖时可进入 no-op，不是当前双仓主路径的唯一前提。

结论：三者是互补关系，不是“谁替代谁”的关系。

---

## 7) 外部依赖与运行时边界审计

关键边界（都影响“是否能真正用起来”）：

1. 网络边界：WebSocket 可达性、NAT/LAN 条件、mesh 直连条件。
2. 运行时边界：Python 环境、Android 权限、后台保活、模型加载。
3. 模型边界：云模型/本地模型可用性、超时、降级策略。
4. 壳层边界：桌面 shell 与系统权限集成程度。
5. 多模态边界：语音/截图/视觉输入输出是否贯通到同一任务链。

当前状态：基础能力有，但“全边界统一可操作、可观测、可恢复”未完成。

---

## 8) operator panel / dashboard / shell 完整体验审计

完整系统应提供：

- 一个统一操作者面板，能看同一任务在多设备上的完整路径；
- 能直接执行控制动作（重试、切换设备、暂停、回滚）；
- 能看到失败原因和下一步建议；
- 能看到中心决策理由与证据。

当前代码现实：

- `windows_client/status_board_v2/` 主要是状态展示。
- `static/operator-console/index.html` 是基础控制台，不是完整全栈控制面。
- `dashboard/frontend/` 未形成 TypeScript 全栈工程。

结论：panel 不完整 = 系统不完整，不是“界面待优化”这么简单。

## 9) 从“能跑”到“成熟可用”还要补什么（分仓分层清单）

### 9.1 V2（后端/编排）

- 补统一多设备规划与失败恢复策略。
- 补任务级持久状态机与可重放证据链。
- 补操作者可见的决策理由输出。

### 9.2 Android（端执行）

- 补协作角色切换策略（自执行/被委托/协同）的一致语义。
- 补极端网络下结果一致性与恢复证明。
- 补多模态输入输出在任务级别的稳定闭环证据。

### 9.3 TypeScript / 全栈

- 建立真实可用的 TypeScript operator 控制台（非静态演示页）。
- 建立 typed contract（API/事件）与可追踪前端状态模型。
- 补任务全链路可视化与交互控制能力。

### 9.4 operator panel / dashboard

- 把 runtime truth 与可操作动作放到同一界面，不再“看板”和“控制”分裂。
- 提供跨设备任务钻取、失败定位、恢复入口。

### 9.5 desktop shell

- 建立真正可交互的桌面助手壳层，而不只是 CLI/状态面。
- 补三态呈现与任务生命周期联动。

### 9.6 multimodal IO

- 统一语音、文本、视觉输入到同一任务编排；
- 统一输出到面板、桌面态、设备态。

### 9.7 中心智能体机制设计

- 建立“规划→执行→验收→记忆→再规划”闭环机制，且操作者可见。
- 建立跨设备协作策略引擎与策略回放验证。

### 9.8 外部集成

- 明确 NATS/mesh/WebSocket 在不同部署拓扑下的启停与回退规则。
- 明确模型服务、权限系统、桌面壳依赖的可运维标准。

## 10) 一个完整可用体验应该是怎样（不用术语）

用户说一句话后：

1. 系统马上告诉你“谁来做、怎么做、预计多久”；
2. 你能看到任务在电脑、手机、平板上的实时进展；
3. 某个设备失败时，系统会自动切换或建议你一键切换；
4. 你点一下就能重试/暂停/改派；
5. 最后系统给出结果、证据、失败原因、下次优化建议；
6. 下次类似任务，系统会记住并更快更稳地完成。

当前代码还没把这 6 步全部做成“稳定可用产品”。

---

## 11) 最终判断（2026-05）

- 这套双仓系统已经不是 demo：主链路真实存在。
- 但它还不是“完整成熟可用的一体化中心-分布式智能系统”。
- 核心差距不只是后端，也包括 TypeScript 全栈、panel、desktop shell、多模态交互和中心智能体机制闭环。
- 所以，本次审计结论是：

**“基础主链已成立，完整系统闭环未完成；必须按双仓一体化全栈方式继续建设。”**
