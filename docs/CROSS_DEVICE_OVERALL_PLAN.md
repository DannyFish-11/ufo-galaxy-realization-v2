> 2026-10-19 定稿,所有者批准按整体实施(「拆掉,确实是按整体来」)。原稿是一份协作文档,这里是仓库内的副本;
> 实施进度见末尾「实施进度」一节,每完成一个阶段更新一次。

## 总体原则与术语

中心智能体是唯一做决定、做协调的地方。每台设备按自己的开关（或配对）加入成为成员，也能自己退出。「模式」只说设备，从不限制智能体。

```
          ┌──────────── 中心智能体(跑在哪台设备上,哪台就是「主脑」)────────────┐
          │  理解人 · 做决定 · 协调 —— 经 mesh 协调,经 AIP v3 / NATS 通信            │
          └───────┬──────────┬──────────┬───────────┬──────────────┬─────────────┘
                  │          │          │           │              │
               电脑成员    手机成员    手表成员   Linux / 云载体   家居 / 桥接设备
             (自己的开关)(自己的开关)(配对即接入)(配对 + 载体程序)(智能体发现,你同意)
                  └──── 先登记进 UDM(名册)/ UCM(连接)──── 网络:headscale 自建内网 + 局域网 + mDNS
```

成员经网络接入、先登记，再由中心智能体按模型的判断协调；网络只管找得到、连得上。

**五条原则**

1. 智能体是关键：它理解人、做决定、协调所有成员。它可以跑在 Windows、Mac、Linux 或云上。
2. 不给设备登记死的能力和角色。每台设备当成一个整体交给模型，由模型的泛化能力加上工程流程约束，决定它做什么。
3. 先登录登记，再协调：所有成员先进 UDM（设备名册）和 UCM（连接），再由智能体经 mesh 协调，经 AIP v3 / NATS 通信。
4. 一种消息格式（AIP v3），一张网（Tailscale 自建内网），多种传输（统一传输层 AIPTransport）。mDNS、自建内网是接入和通信的便利，不是门槛。
5. 派发 Agent 属于执行层：先做安卓手机，再扩到别的电脑、Linux、云服务器这些能跑 Agent 的载体。

## 设备接入与登记

每台设备都走同一条线：找到智能体 → 拿凭证 → 连上 → 登记进 UDM / UCM → 进 mesh → 智能体开始协调。自建内网和 mDNS 只管「找得到、连得上」，不管「能不能加入」。

1. **找到智能体**：同一 Wi-Fi 下用 mDNS 自动发现（`_galaxy._tcp`），或手输地址；出门在外用自建内网（headscale）里的地址。
2. **拿凭证**：智能体出一个 6 位配对码（10 分钟内有效，只能用一次）；设备调 `POST /api/v1/pair/claim` 换一枚 24 小时的能力令牌。配了 headscale、且主脑已在内网里时，同时发一把一次性进网钥匙。令牌快到期时，设备自己调 `/api/v1/pair/renew` 续期。
3. **连上**：`/ws/device/{id}`，发 AIP v3 帧，用令牌认证。
4. **登记**：依次写 UDM（设备名册，唯一权威）→ UCM（连接与收发）→ mesh 对端（有内网地址时）→ mesh 会话 → 报能力 → 自动进 mesh 成员表和编队。开了「设备准入」且还没批准的设备，跳过最后一步。
5. **协调**：智能体从名册里看到它，经 mesh 协调、按 AIP v3 下发；结果经 UCM 回来。

**各类设备怎么加入、怎么退出**

| 设备 | 怎么加入 | 怎么退出 |
| --- | --- | --- |
| 另一台电脑 | 打开跨设备 + 配对码（现在是 `device_client`，以后是 Agent 载体） | 关开关或解除配对 |
| 手机 | App 里打开跨设备 + 配对码；不接也能本地自己跑 | 关开关 |
| 手表 | 配对码，配对即接入 | 新增「解除配对」 |
| Linux / 云服务器 | 装 Agent 载体程序 + 配对码 | 解除配对 |
| 家居 / 串口 / 蓝牙设备 | 智能体发现候选，你同意后接入 | 移除（永远要问） |

**本节要改的**

- mDNS 广播、主脑自动入自建内网，不再看电脑的跨设备开关；没配 headscale 就不碰 Tailscale。
- headscale、TURN / STUN 的配置项在面板上一直显示。
- 手表加「解除配对」；V2 加一个凭令牌自己撤销的接口，令牌作废、从名册移除。
- 保持不变：网关鉴权默认开、配对码一次性、陌生设备要在面板确认。

## 跨设备开关：正确语义与拆闸

电脑上的「跨设备」只决定这台电脑作为设备进不进网络；智能体协调已加入的设备，不看它。现在它在 9 类地方拦着智能体，全部按下表处理。

| # | 位置 | 现在 | 改成 |
| --- | --- | --- | --- |
| 1 | 智能体的 `devices__invoke`（`core/device_onboarding/agent_tools.py`） | 本地模式拒绝 | 只看目标在不在名册、在不在线，再过权限门 |
| 2 | REST `POST /api/v1/devices/{id}/command`（`core/routes/devices.py`） | 403 | 同上 |
| 3 | 命令路由的设备下发（`core/routes/command.py`） | 拒绝 | 同上 |
| 4 | 网关 DeviceRouter 三处（分析出要跨设备、单设备派发、多设备派发）与 agent\_bridge | 拒绝 | 同上 |
| 5 | 手机那批：就绪判定里的「V2 开关」、手机发起的目标、接管、WebRTC 信令 | 拒绝，WebRTC 直接断开 | 只看手机自己的开关和就绪状态 |
| 6 | 派给只挂在 NATS 上的 worker | 本地模式不派 | 只看 worker 在不在线 |
| 7 | 工具 `devices__request_cross_device` 和拒绝时的回话 | 教智能体去请求打开模式 | 删掉 |
| 8 | 按钮成员：关一次就把设备接入平面、局域网发现、mDNS、NATS 写成 false | 智能体的设备工具从 9 个剩 1 个 | 成员只留 NATS，另外三项移出按钮 |
| 9 | 启动：本地模式不广播 mDNS、不入自建内网，headscale 配置项不显示 | 手表找不到、出门连不上 | 见上一节 |

**继续跟电脑开关走的（电脑作为设备加入）**

- 桌面把自己登记进 UDM 和 mesh，别的设备才能用这台电脑。
- 电脑自己收到的请求，要不要整件交给别的设备（入口判定）。这条不能拆：入口一判成「跨设备」，本机动作执行器就跳过本机动作，而现在的判法是「在线设备满两台就算」。
- NATS 总线的默认开关、mesh、联邦，以及设备名、mesh 口令这些配置项。

**迁移**：以前关过按钮的人，`.env` 里设备接入、局域网发现、mDNS 被写成了 false。满足「主键也是 false、三项同时是 false」时认定是按钮写的，清回默认，启动日志说一声。

**改名**

- 「主脑」只指中心智能体所在的设备。
- `MasterBrain` 面向人的叫法改成「任务派发（worker）」，只看它自己的开关，开了就拉起 NATS；类名可以不动。
- 选模型那块的「AI 主脑」改叫「模型」。

**测试与文档**

- 要改或删：本地模式拒绝下发的 2 个文件；请求打开模式的 1 个文件（整删）；手表测试里 3 条；启动横幅；desktop\_gate 2 条；按钮成员；面板配置项；网关开关、agent\_bridge、手机就绪判定、WebRTC 一批（约 10 个文件）。
- 要新增：本地模式下智能体让手表做事（端到端）；关过按钮后设备工具还在；手机自己开了能被调用、自己关了不行；mDNS 不分模式；迁移。
- 文档：AGENTS.md、MULTI\_MACHINE\_MODE.md 第零节和第七节、SYSTEM\_STATUS、手表的提示文案和 README。

## 智能体怎么决定设备做什么

模型决定「哪台设备做什么」，工程流程只约束「怎么做」。规则只做过滤（在不在名册、在不在线、有没有权限），不替模型挑设备。现在的模型看得懂设备，不需要再给它写一套设备说明书。

**模型看到的：每台设备一张「整体卡」**（扩充现有的 `devices__list`）

- 是什么：名称、类型、形态（来自 UDM）。
- 能做什么：设备自己报的每个动作，附一句说明；原始能力串原样保留。
- 现在怎么样：在线、电量、网络路径、忙不忙；手表还有能不能打扰。
- 能不能接派发的 Agent：手机、Linux / 云载体是，手表和「手和眼」式的电脑不是。
- 最近做过什么、结果如何（来自任务流程图）。

固定的「感知 / 动作 / 在场」角色不再给模型看。

**工程流程约束：模型必须这样做**

1. 只对名册里、在线的成员下发。
2. 三种下发方式，按事情大小选：单个动作用 `devices__invoke`；整段目标交给能跑 Agent 的载体（新增 `devices__delegate`）；多步、多设备的事写成计划交给执行层（新增 `tasks__plan`，见「任务执行」一节）。
3. 有风险的动作过权限门、自治档位和高风险确认；手表连着时在手表上问。
4. 每次下发必有结果回来：成功、失败原因或超时；模型按结果决定下一步。
5. 所有下发记进任务流程图。

**要改的规则部件**

| 部件 | 现在 | 改成 |
| --- | --- | --- |
| 角色分配（`core/mesh/device_role_allocator.py`） | 按关键词分感知 / 动作 / 在场，写进 BodyMeshRegistry，用来选「主身体」 | 不再参与派发，只留作观测标签 |
| 能力同化（`core/device_onboarding/taxonomy.py`） | 同义词表归成固定能力类 | 保留，只用于检索和过滤，不用于决定 |
| 设备打分、DAG 里的选设备、源端派发选主身体、给手机派目标时挑手机 | 规则挑设备 | 用模型在委派或计划里指定的设备；模型没指定时，规则只给候选排序 |
| 意图路由里的「目标执行」「并行目标」 | 只在主循环出问题、退到降级路径时才走 | 并进主循环的工具 |

## 安卓手机：派发 Agent、接管本地上下文、桥接对话

按你最初的设计：手机打开跨设备并登录后，中心派一个 Agent 到手机；手机上的 agent runtime 接管本地正在跑的上下文，把本地这一整套并进网络。从此手机上的对话就是和中心智能体的对话，上下文还是那一份。手机侧大部分零件已有，缺的是「接入握手、上交上下文、对话回传、交还」这四段。

```
本地模式 ──打开跨设备并登录──▶ 登记 + 附着会话 ──▶ [新] 中心派桥接 Agent ──▶ [新] 上交本地上下文
    ▲                                                                              │
    └──── [新] 上下文交还(摘要 + 未完成事项)◀── 关闭跨设备 ◀── 对话桥接(上行已有,[新] 回传)◀┘
```

从本地到接入再回到本地是一个闭环；要新增的是握手、上交上下文和交还，另外是第 5 步里的回答回传。

**完整流程**

1. **本地模式**：手机自己一整套跑（截图 → 本地视觉模型规划 → 定位 → 无障碍执行），你和本地模型循环对话。不接网也完整可用。
2. **打开跨设备并登录**：配对码拿令牌 → 连上网关 → 登记进 UDM / UCM → 建立附着会话（已有）。
3. **中心派 Agent**（新增）：中心看到手机接入，发一份「桥接 Agent」给手机。里面有：它代表哪个中心智能体、上下文归到哪个会话、手机本地能力怎么变成可调的工具、自治档位和确认规则。
4. **agent runtime 接管本地上下文**（新增）：手机上的 agent runtime 装上桥接 Agent，把本地上下文打包上交：本地对话记录、正在做的目标和循环进度、最近的执行轨迹、当前屏幕状态。中心把它并进同一个会话。
5. **对话桥接**：之后你在手机上说的话进中心智能体的同一个会话（上行已有，当前作为 `task_submit` 变成一轮对话）；中心的回答和进度回到手机界面（回传新增）。中心要动手机时，经桥接 Agent 调手机本地的循环和无障碍能力。
6. **中心协调**：手机和其他成员一样由中心协调；手机自己发起的跨设备目标也交给中心。
7. **断线**：对话会话跨重连保留，附着会话重建，离线队列补发结果（已有）。连不上时手机用本地循环先顶着。
8. **关闭跨设备**（交还新增）：中心把这段对话的摘要和未完成事项交还给手机，控制权交还（交还语义已有），本地循环接着这份上下文继续。

| 安卓 | `AndroidDelegatedFlowBridge` | 把目标执行、并行子任务、接管归到同一个委派流 |

| 安卓 | `ContinuityRecoveryContext` / `OfflineTaskQueue` | 本地连续性、重连、离线补发 |
| V2 | `galaxy_gateway/android/handlers/*` | 登记、`task_submit` 转成中心对话、目标结果、接管、委派信号 |

| V2 | `core/attached_runtime_session_registry.py` | 附着会话登记与重连续接 |

**要新增的（四段，都走下一节的对外 A2A）**

1. **接入握手**：中心 → 手机「派发桥接 Agent」，手机回「已安装」。手机侧的 agent runtime 以现有的委派流和接管执行器为底座。
2. **上交上下文**：手机 → 中心「上下文交接」；V2 并进该手机对话会话的记忆。
3. **对话回传**：中心 → 手机「回答 / 进度」帧，手机界面显示。手机上的话不驱动电脑三态（和手表同一套来源分类）。
4. **交还**：中心 → 手机「上下文交还」（摘要 + 未完成事项），接上现有的控制权交还。

前提：先把第 4 节里 V2 对手机的拦截拆掉（就绪判定里的 V2 开关、手机发起的目标、接管）。

## A2A：内部一套，对外一套

中心智能体内部的多 Agent 协作已经有；对外派发 Agent 的通话协议只有零件，要把它们收成一套带「必达」保证的协议，跑在 AIP v3 上。

**内部 A2A（保持）**：`core/agent_team.py` 六种协作模式（并行、分工、群体、做 / 审分离、流水线、多层混合），在中心进程内通信。

**对外 A2A（新增，由现有零件收拢）**：中心与派出去的 Agent（手机上的桥接 Agent、Linux / 云载体上的 Agent）之间的通话。

- 可以直接用的零件：V2 的委派交接契约（版本、身份、载荷）；手机的委派信号（确认 / 进度 / 结果，带信号号和序号，可重放）；手机的离线队列。
- 每条消息带：协议版本、消息号、序号、会话号、收发双方的 Agent 号、任务号、追踪号、要不要确认。
- 必达：发送方留着没收到确认的消息；接收方按消息号去重；重连后补发未确认的；同一会话按序号排序。
- 载体：设备经现有连接（WebSocket 走自建内网或局域网）；worker 经 NATS（JetStream 持久队列）。

| 消息 | 方向 | 用途 | 现有对应 |
| --- | --- | --- | --- |
| 派发 Agent / 已安装 | 中心 ↔ 载体 | 接入握手，把桥接 Agent 装上 | 无（新增） |
| 上下文交接 | 载体 → 中心 | 本地对话、目标、轨迹、屏幕状态 | 无（新增） |
| 对话消息 | 双向 | 人说的话上行，回答和进度下行 | 上行有（`task_submit`），下行新增 |
| 委派目标 / 进度 / 结果 | 中心 ↔ 载体 | 整段目标交给载体做 | `goal_execution`、委派信号 |
| 工具调用 / 结果 | 双向 | 中心调载体的本地能力；载体向中心要知识或工具 | `command` / `command_result`（一半） |
| 上下文交还 / 召回 | 中心 → 载体 | 关闭跨设备或中心收回 Agent | 控制权交还（一半） |

命名：代码里现在叫「A2A」的，是混合执行里「直接调应用的 API / MCP」那一级（`core/hybrid_executor.py`），和这里的 A2A 不是一回事，改叫「API 直调」，免得混。

## 任务执行：流程图、DAG、顺序与续跑

三种下发方式各走一条执行线，全部记进任务流程图、重启可续跑。现成的 DAG 分层执行接到新的 `tasks__plan` 上，挑设备听模型的。

**四条执行线**

| 下发方式 | 走哪 | 顺序 | 现状 |
| --- | --- | --- | --- |
| 单个动作 `devices__invoke` | 规范派发器 → UCM → 设备 → 结果回来 | 模型调用的先后 | 已有，被开关拦 |
| 委派目标 `devices__delegate` | 对外 A2A → 载体的 agent runtime（手机本地循环、Linux / 云载体）→ 进度与结果 | 载体自己规划 | 新增（手机端执行器已有） |
| 多步计划 `tasks__plan` | 模型写出步骤、依赖、每步用哪台设备 → DAG 分层执行 → 每步走上面两条之一 → 汇总给模型 | 层间按依赖，同层并行 | DAG 执行已有，入口新增 |
| 代码任务、横向扩容 | 任务派发器 → NATS → Go worker 的 Docker 沙箱 | NATS 队列 | 已有，默认关 |

**多步计划怎么接**

- 用现成的 ConstellationRuntime 分层执行：同层并行，失败时重试或重排（DAGEvolver），最后汇总。
- 拆解和挑设备换成模型写的计划，不再由它自己拆、自己打分挑。
- 一步失败的原因回到模型，由模型决定重试、换设备还是问人。

**顺序、并发、队列**

- 多设备同时下发上限 8 台（`GALAXY_MULTI_DEVICE_DISPATCH_LIMIT`，已有）。
- 同一台设备串行（新增）：每台设备一个队列，一台手机不同时做两件界面操作。手机接管已有「同时只接一个」的门；带背压的队列实现已有（`core/queueing/async_queue.py`），拿来用。
- worker 任务用 NATS JetStream 的持久队列（已有）。
- 取消：取消消息到手机、取消登记表已有。

**任务流程图：每个任务都记**

- 记录状态：排队 → 准入 → 规划 → 选路 → 下发 → 运行 → 结果 → 完成或失败。
- 记录关系：依赖、重试、降级、扇出、汇总。
- 随时写盘；重启后只重派没做完、且依赖已完成的；配合派发去重，不重复触发副作用。
- 谁在用：重启恢复、诊断视图；以后模型也从里面看到每台设备最近做过什么。

**旧路径不接**：旧网关编排器（GalaxyOrchestrator / TaskOrchestrator）、规则拆解器（task\_decomposer）、`e2e` 入口都已标为旧路径，保持不接，不再往里加东西。

## 通信与网络

一种消息（AIP v3）、一张网（Tailscale 自建内网加局域网）、多种传输（AIPTransport 自动选路）、一条总线（NATS，给 worker 和消息镜像）。要补的是：桌面版装上传输适配器；网络和总线不再看电脑的模式。

| 层 | 是什么 | 现状 | 要改 |
| --- | --- | --- | --- |
| 消息 | AIP v3，28 类消息（`core/schemas/aip_v3.py`） | 已接通 | 加上对外 A2A 的几类消息 |
| 传输 | AIPTransport：Tailscale P2P、WebSocket、MQTT、TCP、UDP、蓝牙、串口、DBus、CAN；按消息需要选路，失败换下一种，记链路成功率和延迟 | 只在单独部署网关时注册；桌面版一个没装，走 WebSocket 兜底 | 桌面版启动时也注册，避开和主程序重复绑端口 |
| 网络 | headscale 自建内网（手表内嵌 tailnet 进程，手机用 Tailscale App 加钥匙，电脑配对时进内网）、局域网直连、mDNS 发现 | 本地模式下电脑不广播、不入网 | 不看模式（第 3、4 节） |
| 总线 | NATS：7 条流；设备消息镜像；给 worker 派任务；mesh 里不在本机的参与者收活 | 跨设备模式才起 | 「任务派发」开关开了也起 |
| 异构设备 | 家居（Home Assistant 桥）、MCP 驱动、ADB / scrcpy 节点、串口 / CAN / 蓝牙、Matter 发现 | 已有，经设备接入平面变成成员 | 不变；智能体用同一个 `devices__invoke` 调 |

**设备要不要直接接 NATS**：建议不要。手机、手表、电脑继续走 WebSocket 经 UCM，这样登记和连接只有一个权威；NATS 留给服务端参与者（worker、节点、消息镜像）。你设想的「经 NATS 跨设备通信」，在这个方案里是：设备消息镜像到 NATS，任何服务端参与者都听得到。

## 其他载体与手表

做一个通用的「Agent 载体」程序，装在别的电脑、Linux、云服务器上：用配对码接入，接受中心派来的 Agent，在本地跑。手表不是载体，只做人和智能体之间的入口和出口。

**Agent 载体由现有三块拼成**

| 块 | 来自 | 负责 |
| --- | --- | --- |
| 连接层 | `device_client`（Windows / macOS / Linux 已通用） | 配对、令牌续期、进自建内网、找到主脑、保持连接 |
| Agent 运行时 | `core/local_agent_runtime.py` | 收下派来的 Agent，跑推理加行动的循环、顺序执行或自主规划 |
| 代码沙箱 | Go worker 的 Docker 沙箱 | 需要跑代码时隔离执行 |

- 登记时声明「能跑 Agent」以及本机有什么：shell、文件、浏览器、GPU、有没有图形界面。模型在设备整体卡里看到。
- 和中心之间走对外 A2A；中心可以随时召回。
- 派来的 Agent 受同样的权限门和自治档位约束；代码一律在沙箱里跑。
- 模型从哪里来待定：经中心用中心的模型（钥匙只在中心），或载体自己配钥匙。

**别的电脑有两种接法**

- 「手和眼」：只接受截图、点击、输入这类单个动作（现在的 `device_client`，保留）。
- 载体：接受整段目标，自己在本机完成。
- 带三态的桌面接到别处的智能体：需要把三态和智能体拆成两个进程、桌面壳能连远端网关，放在最后一个阶段。

**手表**

- 成员，配对即接入，没有两种模式。
- 上行：你说的话、对提问和决策的回答、可打扰性。下行：智能体的消息、提问、决策。通话。
- 智能体能让它做的：弹通知、震动、报状态。
- 本方案对它的改动：撤掉「先开跨设备」的提示；加「解除配对」；拆闸后任何模式下智能体都能让它做事。
- 仍未解决：手表通话时智能体还不能动手（实时语音没接工具），需要先定实时语音用哪家。
