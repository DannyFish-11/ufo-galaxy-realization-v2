# Supply-Chain & Image Security (PR-G4)

This document describes the supply-chain security controls added in PR-G4:
hash-locked Python dependencies, SBOM generation, cosign image signing, and
per-node security reports.

---

## Overview

| Control | Tool | CI Enforcement |
|---------|------|----------------|
| Dependency hash locking | pip-tools `--generate-hashes` | `supply-chain-hash-gate` (ci.yml) |
| SBOM generation | syft (via anchore/sbom-action) | `sbom-sign` job (supply-chain.yml) |
| Image signing | cosign (keyless, Sigstore OIDC) | `sbom-sign` job (supply-chain.yml) |
| Signature verification | cosign verify-blob | `sbom-sign` job (self-check) |
| Per-node security reports | `scripts/gen_node_security_report.py` | `node-security-report` job |

## 1 — Hash-Locked Python Dependencies

### How it works

The file `requirements.hash.txt` is a **fully-pinned, hash-annotated** lock
file generated by [pip-tools](https://github.com/jazzband/pip-tools).  It
covers the core framework, network, and security packages listed in
`requirements.in`.  Every package entry includes one or more `sha256` hashes
that pip verifies at download time, preventing substitution attacks.

```
# excerpt from requirements.hash.txt
fastapi==0.115.11 \
    --hash=sha256:... \
    --hash=sha256:...
```

When CI runs `pip install --require-hashes -r requirements.hash.txt`, pip
**rejects any package** whose downloaded content does not match the committed
hash — even if the package name and version are correct.

### Regenerating requirements.hash.txt

Run the helper script whenever you bump a dependency in `requirements.in`:

```bash
# Requires pip-tools — installed automatically by the script
scripts/pin_deps.sh
```

The script:
1. Calls `pip-compile --generate-hashes` against `requirements.in`.
2. Overwrites `requirements.hash.txt`.
3. Reminds you to commit the updated file.

To verify the committed file matches the current resolution (without
overwriting):

```bash
scripts/pin_deps.sh --verify
```

### Adding or updating a dependency

1. Edit `requirements.in` (direct runtime deps only).
2. Run `scripts/pin_deps.sh` to regenerate the hash file.
3. Commit **both** `requirements.in` **and** `requirements.hash.txt`.
4. The CI `supply-chain-hash-gate` job will verify the file on every PR.

> **Note**: `requirements.txt` (full production deps) continues to be used for
> regular installs; `requirements.hash.txt` covers only the security-critical
> subset.  Extend `requirements.in` to add more packages to the hash-checked
> scope.

## 2 — SBOM Generation

An **SBOM (Software Bill of Materials)** lists every package included in a
built container image.  Galaxy uses [syft](https://github.com/anchore/syft)
(via the `anchore/sbom-action` GitHub Action) to generate SBOM files in
**SPDX JSON** format.

### CI behaviour

The `sbom-sign` job in `.github/workflows/supply-chain.yml` runs on every push
to `main`:

1. Builds each matrix image (`galaxy-main`, `galaxy-gateway`, `galaxy-node`).
2. Calls `anchore/sbom-action` to generate `<image>.sbom.spdx.json`.
3. Signs the SBOM blob with cosign (see §3).
4. Uploads the SBOM + signature pair as a 90-day retained CI artifact.

### Generating an SBOM locally

```bash
# Install syft
brew install syft          # macOS
curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh | sh

# Generate SBOM for the main Galaxy image
docker build -t galaxy-main:local .
syft galaxy-main:local -o spdx-json > galaxy-main.sbom.spdx.json

# Or for a node image
docker build --build-arg NODE_NAME=Node_02_Tasker -f Dockerfile.node \
    -t galaxy-node-tasker:local .
syft galaxy-node-tasker:local -o spdx-json > galaxy-node-tasker.sbom.spdx.json
```

## 3 — cosign Image Signing & Verification

Galaxy uses [cosign](https://github.com/sigstore/cosign) with **keyless
signing** backed by GitHub Actions OIDC.  No long-lived keys are stored;
instead, cosign obtains a short-lived certificate from Sigstore Fulcio,
anchored to the GitHub Actions identity.

### Signing in CI (automatic)

The `sbom-sign` job runs `cosign sign-blob` against each SBOM file:

```yaml
cosign sign-blob \
  --yes \
  --output-signature "${{ matrix.name }}.sbom.sig" \
  "${{ matrix.name }}.sbom.spdx.json"
```

The resulting `.sig` file (a base64-encoded bundle) is uploaded alongside the
SBOM artifact.

### Verifying signatures locally

```bash
# Install cosign
brew install cosign     # macOS
# Or: go install github.com/sigstore/cosign/v2/cmd/cosign@latest

# Download the SBOM and signature from the CI artifact, then:
cosign verify-blob \
  --signature galaxy-main.sbom.sig \
  --certificate-identity-regexp "https://github.com/DannyFish-11/ufo-galaxy-realization-v2/*" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  galaxy-main.sbom.spdx.json
```

A successful verification prints:

```
Verified OK
```

> **On PRs**: Signing is skipped on PR builds (untrusted code must not produce
> signed artifacts). The `sbom-sign` job only runs on pushes to `main` and
> scheduled/manual workflow dispatches.

## 4 — Per-Node Security Reports

The script `scripts/gen_node_security_report.py` generates a lightweight JSON
security report for each Galaxy node image.  It is run by the
`node-security-report` CI job and uploads all reports as a single artifact.

### What the report contains

Each `<NodeName>.security.json` file includes:

| Field | Description |
|-------|-------------|
| `node` | Node directory name |
| `image.ref` | Docker image reference |
| `image.digest` | Digest (if Docker is available) |
| `sbom.present` | Whether an SBOM file was found |
| `sbom.component_count` | Number of components in the SBOM |
| `signature.verified` | Whether cosign verification passed |
| `hash_locked` | Whether `requirements.hash.txt` is present |
| `supply_chain_checks` | Consolidated pass/fail summary |

A combined `security-summary.json` is also generated with aggregate counts
across all nodes.

### Running the report locally

```bash
# All discovered nodes (no Docker/cosign required)
python scripts/gen_node_security_report.py \
    --no-sig-check \
    --output-dir /tmp/security-reports

# Specific nodes with SBOM directory
python scripts/gen_node_security_report.py \
    --nodes Node_02_Tasker Node_04_Router \
    --sbom-dir /tmp/sboms \
    --output-dir /tmp/security-reports

# List all discovered nodes
python scripts/gen_node_security_report.py --list-nodes

# Text format (human-readable)
python scripts/gen_node_security_report.py \
    --no-sig-check \
    --format text \
    --output-dir /tmp/security-reports
```

## 5 — CI Jobs Reference

### `supply-chain-hash-gate` (ci.yml)

Runs on every push and PR.  Blocks merge if:
- `requirements.hash.txt` is absent.
- `pip install --require-hashes` fails for any package.

### `hash-verify` (supply-chain.yml)

Runs when dependency files or Dockerfiles change, and on schedule.  Checks:
- `requirements.hash.txt` exists.
- Hash file matches a fresh `pip-compile --generate-hashes` run.
- Hash-verified install succeeds.

### `sbom-sign` (supply-chain.yml)

Runs on pushes to `main`.  For each matrix image:
1. Builds the Docker image.
2. Generates SPDX JSON SBOM via syft.
3. Signs the SBOM blob with cosign (keyless).
4. Verifies the signature immediately.
5. Uploads SBOM + sig as 90-day artifact.

### `node-security-report` (supply-chain.yml)

Runs on every supply-chain workflow trigger.  Generates JSON reports for all
Galaxy node directories and validates the combined summary schema.

## 6 — FAQ

**Q: Can I use a different SBOM format?**
Yes. Change the `format:` field in the `anchore/sbom-action` step from
`spdx-json` to `cyclonedx-json` (or others supported by syft).

**Q: How do I rotate or revoke a signed artifact?**
Keyless signing with Sigstore does not require key rotation.  Each signature
has a short-lived certificate with an embedded timestamp.  To "revoke", simply
stop referencing the old artifact and re-sign after rebuilding from a clean
state.

**Q: Why only core packages in requirements.hash.txt?**
The full `requirements.txt` includes platform-specific and optional packages
(PyQt5, PyWin32, device SDKs) that are difficult to hash-lock across all
platforms simultaneously.  The core subset covers the packages most exposed
to supply-chain risk (web framework, cryptography, auth).  Add entries to
`requirements.in` to extend coverage as needed.

**Q: Where are the CI artifacts stored?**
SBOM and security report artifacts are retained for 90 days in GitHub Actions
and can be downloaded from the Actions run page or via the GitHub API.
